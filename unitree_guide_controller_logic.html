UnitreeGuideController.cpp 运行逻辑梳理

这份文档专门解释 src/quadruped_ros2_control-humble/controllers/unitree_guide_controller/src/UnitreeGuideController.cpp 的代码结构、生命周期、数据流和控制责任。目标是读完后，能完整理解这个控制器在 Gazebo Classic / ros2_control 框架中的位置和作用。

定位

这个文件在整个系统里是什么角色

UnitreeGuideController 是一个继承自 controller_interface::ControllerInterface 的 ROS2 控制器插件， 它不是 Gazebo 插件，也不是底层硬件接口，而是“高层运动控制器”。

它负责什么

  • 声明自己要使用哪些 command/state interfaces
  • 创建估计器、机器人模型、平衡控制器和步态器
  • 把 ros2_control 接口借出来，装配成内部统一的 CtrlInterfaces
  • 管理 FSM 状态列表，并每周期驱动当前状态执行

它不负责什么

  • 不直接实现 Gazebo 物理仿真
  • 不直接读取 Gazebo 组件
  • 不自己创建底层关节接口
  • Classic 模式下不直接算最终 torque 写入 Gazebo 关节，而是经由 leg_pd_controller
头文件结构

类成员和数据骨架

从头文件 include/unitree_guide_controller/UnitreeGuideController.h 可以先建立整体结构感。

成员 作用
CtrlComponent ctrl_component_ 算法对象容器，里面放 robot_model_、estimator_、balance_ctrl_、wave_generator_、convex_mpc_。
CtrlInterfaces ctrl_interfaces_ 接口容器，里面放 ros2_control 借来的 command/state 接口、控制输入缓存、调试 publisher、节点指针等。
FSMStateList state_list_ 保存所有 FSM 状态对象，比如 passive、fixedDown、fixedStand、trotting。
current_state_ / next_state_ 当前状态和待切换状态。
command_interface_map_ 把接口名 effort/position/velocity/kp/kd 映射到 CtrlInterfaces 中对应的容器。
state_interface_map_ 把 position/velocity/effort 状态口映射到状态容器。
imu_name_ / feet_names_ / base_name_ 告诉控制器：IMU 叫什么、基座叫什么、四只脚叫什么，从而让 URDF/接口和控制代码对齐。
先把这个类看成一个“总装配器”：它本身不含所有控制算法细节，但负责把接口、参数、模型、状态机和调试工具组织起来。
依赖对象

CtrlComponent 和 CtrlInterfaces 分别是什么

CtrlComponent

文件：control/CtrlComponent.h

  • robot_model_：机器人运动学/动力学抽象
  • estimator_：机身状态估计
  • balance_ctrl_：平衡控制
  • wave_generator_：步态相位生成器
  • convex_mpc_：MPC 求解器

它更像“算法资源仓库”。

CtrlInterfaces

文件：libraries/controller_common/include/controller_common/CtrlInterfaces.h

  • 关节命令接口：torque/position/velocity/kp/kd
  • 关节状态接口：position/velocity/effort
  • IMU 状态接口
  • 控制输入缓存：control_inputs_
  • 调试发布器和节点指针

它更像“运行时接口总线”。

生命周期

整个控制器的运行主线

1. on_init()：声明参数，准备接口类型和估计器。
↓
2. on_configure()：建立输入订阅，等待 /robot_description，创建机器人模型、平衡控制器、MPC、步态生成器。
↓
3. on_activate()：把 ros2_control 借来的接口分类装入 CtrlInterfaces，创建 FSM 状态对象，初始化当前状态。
↓
4. update()：每个控制周期都执行，更新模型、估计器、TF、调试消息和 FSM 状态机。
↓
5. on_deactivate()/cleanup()/shutdown()：释放接口，结束生命周期。
逐函数解释

核心函数到底做了什么

1. command_interface_configuration()

代码位置：UnitreeGuideController.cpp:17-38。 它告诉 ros2_control：“我要哪些命令接口”。

  • 遍历 joint_names_ 和 command_interface_types_
  • 如果 command_prefix_ 非空，就生成 leg_pd_controller/FR_hip_joint/position 这类带前缀接口名
  • 否则直接生成 FR_hip_joint/position 这类接口名

这正是 Gazebo Classic 方案里“主控制器把命令发给 leg_pd_controller 而不是直接发给底层关节”的关键。

2. state_interface_configuration()

代码位置：UnitreeGuideController.cpp:40-59。 它声明自己要读取哪些状态接口。

  • 所有关节的 position/velocity/effort
  • IMU 的四元数、角速度、线加速度

后面 on_activate() 真正拿到的 state_interfaces_，就是按这份需求借出来的。

3. on_init()

代码位置：UnitreeGuideController.cpp:194-230。 这是“参数声明和基础对象准备阶段”。

  • 声明并读取 joints、command_interfaces、state_interfaces
  • 声明并读取 imu_name、base_name、command_prefix、feet_names
  • 读取站立姿态参数：down_pos、stand_pos、stand_kp、stand_kd
  • 读取控制频率 update_rate 到 ctrl_interfaces_.frequency_
  • 创建 Estimator 对象

此时还没有机器人模型，也还没有借到实际接口，所以这里只能做“轻量初始化”。

4. on_configure()

代码位置：UnitreeGuideController.cpp:232-259。 这是“建立运行依赖”的阶段。

  • 订阅 /control_input，把遥控/键盘输入写进 ctrl_interfaces_.control_inputs_
  • 订阅 /robot_description，收到 URDF 后创建 QuadrupedRobot
  • 在同一个回调里创建 BalanceCtrl 和 ConvexMpcSolver
  • 创建 WaveGenerator

这里的一个设计重点是：机器人模型不是写死在构造函数里，而是等 robot_description 真正到达后再创建， 这样控制器可以根据 launch 时注入的实际 URDF 动态构建模型。

5. on_activate()

代码位置：UnitreeGuideController.cpp:261-321。 这是“正式接通 ros2_control 接口并进入可运行状态”的阶段。

  • 最先设置 ctrl_interfaces_.node 和两个调试 publisher
  • 创建 tf_broadcaster_
  • 调用 ctrl_interfaces_.clear() 清掉旧引用
  • 遍历 command_interfaces_，按接口名分类塞到 joint_torque_command_interface_、joint_position_command_interface_ 等容器
  • 遍历 state_interfaces_，把 IMU 接口和关节接口分开存放
  • 创建所有 FSM 状态对象
  • 将当前状态初始化为 passive，并调用 enter()

这一步完成后，控制器才真正具备“读写接口”和“切换状态”的能力。

6. update()

代码位置：UnitreeGuideController.cpp:61-192。 这是整个文件最核心的周期函数，每个控制周期都会被 controller_manager 调用。

  • 如果 robot_model_ 还没准备好，直接返回
  • 依次更新 robot_model_、wave_generator_、estimator_
  • 发布机身 world -> base 的 TF
  • 发布调试消息 /body_debug
  • 最后执行 FSM 调度和状态切换
周期数据流

update() 每一拍到底发生了什么

controller_manager 调用 update(time, period)
        ↓
检查 robot_model_ 是否已建立
        ↓
robot_model_->update()
  读取关节接口，更新腿运动学和机身相关模型量
        ↓
wave_generator_->update()
  推进步态相位，判断四条腿当前是支撑还是摆动
        ↓
estimator_->update()
  结合 IMU、关节和足端信息估计机身位置/速度/姿态
        ↓
发布 TF: world -> base
        ↓
发布 body_debug 调试消息
        ↓
FSM 调度：
  NORMAL:
    先 checkChange()
    若要切状态 -> mode = CHANGE
    若不切状态 -> current_state_->run()
  CHANGE:
    current_state_->exit()
    切到 next_state_
    current_state_->enter()
    mode = NORMAL
代码里特意把状态机调度放在 update() 最后，这是作者自己在注释里强调的修改点。这样可以避免新状态“漏掉一拍”。
FSM

状态机是怎么挂进来的

头文件里定义了 FSMStateList，里面包含： passive、fixedDown、fixedStand、freeStand、 swingTest、balanceTest、trotting。

每个状态都继承自 FSMState，必须实现：

  • enter()：进入状态时执行
  • run(time, period)：正常运行时每拍执行
  • exit()：退出状态时执行
  • checkChange()：判断要不要切到别的状态

UnitreeGuideController 自己并不决定 trotting 里每条腿怎么摆，而是把“当前状态要干什么”委托给对应状态类。

Classic 特性

为什么这里会出现 command_prefix_

这是 Gazebo Classic 路线最重要的适配点之一。

在 gazebo.yaml 中，unitree_guide_controller 设置了： 

command_prefix: "leg_pd_controller"

所以主控制器申请的命令口实际上会变成： 

leg_pd_controller/FR_hip_joint/position
leg_pd_controller/FR_hip_joint/velocity
leg_pd_controller/FR_hip_joint/effort
leg_pd_controller/FR_hip_joint/kp
leg_pd_controller/FR_hip_joint/kd
...

这意味着：

  • UnitreeGuideController 输出的是 PD 目标和前馈力矩
  • leg_pd_controller 再结合当前状态计算最终 torque
  • 最终 torque 才通过底层 effort 接口进入 Gazebo

总结

一句话总结这个文件

UnitreeGuideController.cpp 的本质不是“具体走路算法本体”，而是 高层控制器装配与调度中心： 它负责把 ros2_control 接口、机器人模型、估计器、平衡控制器、步态生成器和 FSM 状态机组织起来，并在每个控制周期按固定顺序驱动它们运行。
